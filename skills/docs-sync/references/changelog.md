# The changelog

One entry per merged or about-to-merge piece of work — normally one PR. The entry says
what changed for a user or a developer, in one line, with the issue or PR reference.

## Find the file

Look, in this order, for a changelog the project already keeps:

1. `CHANGELOG.md` at the project root (also `CHANGELOG`, `CHANGES.md`, `HISTORY.md`,
   `RELEASES.md`, any letter case).
2. `docs/CHANGELOG.md` or `docs/changelog.md`.
3. Per-app or per-package changelogs (`apps/*/CHANGELOG.md`, `packages/*/CHANGELOG.md`).

If only per-package changelogs exist, the entry goes in the changelog of each app or
package the change touched. If both a root file and per-package files exist, ask which
the team maintains by hand.

## Check whether a tool owns it

Before planning a hand-written entry, check for a release tool: a `.changeset/` folder,
or release configuration or a release script in `package.json` or the repository root
that generates the changelog from commits.

If the changelog is generated, **do not edit it.** Say which tool was found, plan no
changelog edit, and report it under "skipped — generated by a tool". Do not create the
tool's own input files either; tell the developer what the tool expects.

## Follow the existing format

Read the file's most recent entries and copy their shape exactly:

| Observe | Follow |
| --- | --- |
| Where new entries go (top or bottom; under an `Unreleased` heading; under a date or a version) | Put the entry in the same place |
| Heading style (date, version, both) | Use the same; never invent a version number |
| Grouping (`Added` / `Changed` / `Fixed` / …, or by area, or none) | Use an existing group; add a group only if the format clearly uses that set |
| Bullet style, tense, capitalisation, full stop or not | Match |
| How references are written (`#12`, `(#12)`, a full link, issue vs PR) | Match |
| Date format | Match |

If a section for the current date or `Unreleased` already exists, add to it rather than
starting a second one. Existing entries are never reworded, reordered, or removed.

## When there is no changelog

Do not create one silently. In the plan, propose the file and the format below, and ask.
Creating the file needs its own explicit yes.

```markdown
# Changelog

Changes to this project, newest first. One line per merged piece of work.

## <YYYY-MM-DD>

### Added

- <What a user or developer can now do> (#<pr>)

### Changed

- <What behaves differently> (#<pr>)

### Fixed

- <What was wrong and is now right> (#<pr>)
```

Only the groups that have an entry are written. If the developer wants a different
format, use theirs.

## Writing the entry

- **One line.** What changed, as the reader meets it — not how it was implemented, and
  not the commit subject copied over.
- **User-visible first.** "Users can resume a saved draft from the list screen." If the
  change has no user-visible effect, write the developer-visible one: a new script, a new
  package, a changed convention, a new environment variable.
- **One entry per piece of work.** Several commits in one PR are one entry. A PR that
  really does two unrelated things gets two lines with the same reference.
- **The reference** is the PR number when there is one, and the issue number as well if
  the existing format shows both. No PR and no issue → write the entry without a
  reference and say so in the plan.
- **The date** (for dated formats) is the merge date for a merged PR, otherwise today's.
- **The group** — `Added` for something new, `Changed` for different behaviour, `Fixed`
  for a bug, `Removed` for something taken away.
- **Nothing sensitive** — no credentials, internal URLs with secrets, or personal data.
- **Not worth an entry:** a change that only touches documents, or formatting-only
  changes. Say it was skipped as "no user- or developer-visible change" and let the
  developer overrule.

## Not adding it twice

Before planning the entry, search the changelog for the PR number and the issue number
in any of the forms the file uses. If either is already there, the entry exists — skip
it. For work with no reference, skip when a line with the same meaning is already under
the same heading.

If the existing entry is wrong, show the developer; do not edit it unless they ask for
that specific correction.
